Before contributing code or adding/removing crates (see [Workspace Layering & Isolation Boundaries](/en/dev/) and [Cordis Microkernel & Adding Tools](/en/dev/cordis/)), align with these strict repository conventions. Most violations are caught directly by clippy `-D warnings` or CI feature-matrix builds.

## Module Layout & Dependency Constraints

- **No `mod.rs`**: Always use modern Rust module layout `src/foo.rs` + `src/foo/bar.rs`. Use `use crate::xxx` in production modules and `use super::*;` consistently inside unit test modules.
- **Documentation & reference repo boundary**: Every crate should begin with Chinese `//!` module docs noting its corresponding upstream reference path (a few historical exceptions exist, such as `mizar-llm-http`). The `references/` directory is excluded via `.gitignore` for design cross-checking only—**never `git add` it**.
- **Workspace dependency management**: The root `Cargo.toml` has no `[package]`; all versions are centralized in `[workspace.dependencies]`, and sub-crates always specify `{ workspace = true }` and `[lints] workspace = true`.
- **Error handling & locking conventions**: Public error types use `thiserror` and unify onto `cordis::BoxError`; do not introduce `anyhow`. Using `.lock().unwrap()` is an accepted convention across the codebase—do not wrap it or swap in `parking_lot`.

## Bilingual Copy Contract (Do Not Unify Into One Language!)

Tool schemas, comments, and UI strings follow a strict language split by consumer—never flatten everything into only Chinese or only English for "consistency":

| Location | Required Language | Reason |
| :--- | :--- | :--- |
| `//!` module docs & inline comments | Chinese | Matches architecture docs and upstream reference mappings |
| Tool `description` & parameter schema descriptions | **English** | Injected directly into model context; switching to Chinese measurably degrades tool-calling accuracy |
| Tool runtime validation errors (e.g., missing arg) | Chinese (e.g., `"缺少 path 参数"`, *"missing path parameter"*) | Direct, human-readable troubleshooting feedback |
| TUI copy & commit messages | Chinese or English | Clarity and accuracy take precedence |

## `pi-emphasis` Two-Way Contract & Cross-Crate Changes

- **Two-way UI contract**: `reply_guidance_prompt()` in `crates/mizar-tui-ui/src/emphasis.rs` generates formatting instructions fed to the model, and the renderer in the same file parses and styles those markers for terminal emphasis. **Changing the generator requires updating the renderer in lockstep, with paired unit tests asserting both ends**.
- **Cross-crate shared enum & struct coupling**: `OverlayKind`, `OverlayAction`, and `UiEvent` in `mizar-tui-ui` have numerous constructors and pattern matches inside `mizar-tui`. Whenever you change one of these enums or fields, run a full `cargo check --workspace` rather than checking a single crate.

## Feature Gating & Testing Rules

`mizar-agent-spine` defines six optional features: `legacy`, `coding`, `compaction`, `sqlite`, `trajectory`, and `router`. Every `use` statement referencing an optional dependency must carry a matching `#[cfg(feature = "...")]`, or stripped builds will immediately fail to compile.

```bash title="Required minimal feature-gate verification"
# Verify the library and test targets compile with all optional features disabled
cargo check --locked -p mizar-agent-spine --no-default-features --all-targets
```

Follow three concrete conventions when writing tests:

1. **No `tempfile` dependency**: The workspace intentionally omits the `tempfile` crate; build temporary test directories via `std::env::temp_dir().join(format!("mizar_xxx_{}", std::process::id()))` and clean them up afterward.
2. **Explicit integration test registration**: `mizar-agent-spine` integration tests are aggregated in `tests/integration/main.rs` behind `#[cfg(feature)]` gates—any new integration test module must also be registered in `main.rs`.
3. **Sequential compat test numbering & zero skipped tests**: `crates/cordis/tests/compat.rs` tracks upstream test cases sequentially as `compat_NN_<description>`. Every new behavior must ship with deterministic fail-on-regression assertions; never mask timing flakiness with `#[ignore]` or retries.

## Standard CI Checks & Commit Conventions

<Callout type="important" title="Verified must only list commands actually run in this round">
  The <code>Verified:</code> section of a commit message may only list real command results you personally ran and observed passing <strong>after your final edit</strong>. Do not add AI attribution, and summarize cross-crate changes grouped by crate with a focus on intent (why) rather than restating the diff.
</Callout>

```text title="Standard commit message template"
feat(scope,scope): one-line summary of the core change

- Explain rationale and design trade-offs, grouped by crate.

Verified:
- cargo clippy --workspace --all-targets -- -D warnings: passed (0 warnings).
- cargo test --workspace: passed (0 failed).
```

`cordis` decouples and wires subsystems together through plugin registration, contextual dependency injection, and lifecycle management. Writing a tool plugin, integrating a new LLM protocol (see `crates/mizar-llm-mock/src/lib.rs`), or attaching event listeners all follow the same contract.

## Minimal Runnable Tool Plugin (41 Lines)

The shortest canonical reference implementation in the repo lives at `crates/mizar-tool-time/src/lib.rs`:

```rust title="crates/mizar-tool-time/src/lib.rs"
use chrono::Local;
use cordis::{BoxError, BoxFuture, Cleanup, Context, Inject, Plugin};
use mizar_tools::{ToolDefinition, ToolsContextExt};
use serde_json::json;

#[derive(Default, Clone, Copy)]
pub struct ToolTimePlugin;

impl Plugin for ToolTimePlugin {
    type Config = ();

    fn name(&self) -> Option<&str> {
        Some("tool-time") // kebab-case plugin name
    }

    fn inject(&self) -> Inject {
        Inject::from(["tools"]) // camelCase service name
    }

    fn apply(
        &self,
        ctx: Context,
        _config: Self::Config,
    ) -> BoxFuture<'static, Result<Option<Cleanup>, BoxError>> {
        Box::pin(async move {
            let tools = ctx.tools()?;
            ctx.effect("tool-time.register", || {
                Ok::<_, mizar_tools::ToolError>(Some(tools.register(
                    ToolDefinition::sync_tool(
                        "get_time",
                        "Get current local date and time.",
                        json!({ "type": "object", "properties": {} }),
                        |_args, _exec| {
                            Ok::<_, BoxError>(
                                Local::now().format("%Y/%m/%d %H:%M:%S").to_string(),
                            )
                        },
                    ),
                )?))
            })?;
            Ok(None)
        })
    }
}
```

<Callout type="warning" title="Common pitfall: omitting fn inject() does not panic">
  If you call <code>ctx.tools()?</code> or another <code>ctx.service()</code> inside <code>apply</code> without declaring the corresponding service name in <code>fn inject()</code>, <code>cordis</code> will <strong>not</strong> panic on the spot—instead it returns a <code>MissingInject</code> error, placing the plugin into the <code>FAILED</code> state and causing its tools to <strong>silently disappear</strong>, which is far harder to debug than a panic.
</Callout>

## `inject` / `provide` and `ctx.effect` Invariants

- **Service naming and accessors**: Standard `cordis` service names uniformly use camelCase (`llm`, `tools`, `sessions`, `systemPrompt`, `agentLoop`, `skills`, `mcp`, `trajectory`, `compaction`, `spinePlugins`). Production code must always call `<Name>ContextExt` extension methods (such as `ctx.tools()?`) rather than querying the service map directly.
- **Side effects must go through `ctx.effect("<crate>-<action>", ...)`**: Returned cleanup handles are managed by the framework. When a plugin unloads or reloads, the Fiber state machine guarantees **automatic cleanup in reverse registration order** for every side effect (unregistering tools, stopping background tasks)—the core invariant that prevents resource leaks.

## Tool Visibility (`ToolExposure`) & Three-Stage Pipeline

When registering a tool, choose its `ToolExposure` deliberately; picking the wrong level leaves a tool silently unavailable:

| `ToolExposure` Variant | Semantics | Typical Use Case |
| :--- | :--- | :--- |
| `Direct` | Exposed directly to the LLM and callable from the sandbox | Core built-in tools (`read` / `bash` / `grep`) |
| `ModelOnly` | Visible to the LLM, barred from recursive sandbox calls | Meta-tools (`codemode` / `tool_search`) |
| `Codemode` | Declared only inside the sandbox; zero first-turn prompt cost | Default for external MCP tools |
| `Deferred` | Hidden by default; discoverable only via `tool_search` | Large or niche services |
| `Hidden` | Completely hidden from both model and sandbox | Project-disabled tools |

`crates/mizar-tools/src/lib.rs` chains three waterfall hooks around tool execution (validation/interception, execution wrapping, and output post-processing). Any new tool that writes or modifies files at a path must serialize via `with_file_mutation_queue` to prevent concurrent tool calls from clobbering one another.

## Five Event Dispatch Semantics in `cordis`

In `crates/cordis/src/events.rs`, plugins coordinate loosely via the event bus using five dispatch modes:

- `dispatch`: Invokes listeners sequentially one by one.
- `bail`: Invokes listeners sequentially until one returns `Some(result)`, short-circuiting immediately.
- `waterfall`: Pipes and transforms a value sequentially down the chain (the core mechanism behind the tool pipeline).
- `parallel`: Executes all subscribed handlers concurrently and aggregates results.
- `emit`: Fires a notification without waiting for return values (suitable for metrics or log syncing).

## Wiring a New Plugin Into the Host

1. Follow the root `Cargo.toml` convention: declare the new crate or third-party version under `[workspace.dependencies]`, and use `{ workspace = true }` plus `[lints] workspace = true` inside the sub-crate (see [Engineering Conventions, Gating & Testing](/en/dev/conventions/)).
2. Register the plugin in the `apply` assembly chain inside `crates/mizar-agent-spine/src/lib.rs` (optional plugins must be gated with `#[cfg(feature = "...")]` and matching optional dependencies; see [Workspace Layering & Isolation Boundaries](/en/dev/)).
3. Update the authoritative **`docs/plugins.md`** crate table and topology diagram in lockstep so docs and the dependency graph stay strictly in sync.

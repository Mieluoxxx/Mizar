By default, Mizar persists every conversation turn, tool result, and branch node to a local single-file database at `~/.mizar/sessions.sqlite` (using single-writer WAL mode so UI rendering never stutters and sudden terminal crashes don't corrupt history). When you exit Mizar, the terminal prints the exact resume command so you can pick up right where you left off (see [CLI Flags](/en/tui/cli/) for more startup options):

```bash title="Continue or resume sessions after exiting"
# Immediately resume the most recent session in the current workspace
mizar -c

# Open an interactive picker to choose any past session by time or turn count
mizar --resume

# Disable writing to disk in read-only containers or one-off scratch runs
mizar --no-persist
```

You can also override the database file location via the `MIZAR_SESSION_DB` environment variable, or set it to `none` / `off` to disable disk persistence globally. When you want to share your investigation with a teammate for review, run `/export` to export the session in one command (see [Commands](/en/tui/commands/) for other session controls).

## Forking From Any Turn With `/tree`

When you're halfway through Approach A, realize the architecture feels wrong, and want to rewind to turn 4 to try Approach B without deleting Approach A, you don't need to `git reset` your repo or start a blank session.

Run `/tree` in the input box:

1. The UI expands the entire session tree organized by parent-child relationships (cleanly preserving both regular turns and `!` / `!!` local shell records);
2. Use the arrow keys to highlight the historical node you want to rewind to and press Enter;
3. Asking a new question from that node creates a brand-new parallel branch—both lines of exploration coexist intact in history, and you can reopen `/tree` anytime to jump back to the original node and compare.

## Context Compaction (`/compact`) & FTS5 Episodic Recall

When long sessions approach the context budget, `mizar-compaction`, `mizar-session-sqlite`, and `mizar-recall` work together to reclaim window headroom without discarding historical details:

- **Progressive compaction & manual `/compact [focus]`**: Before each step, L1 prunes oversized prior tool outputs without calling an LLM (retaining head/tail excerpts and a recall handle). If pressure remains above threshold (or you run `/compact keep refactor decisions`), L2 builds a deterministic `<mizar-digest>` plus a checkpoint summary using prefix-cache-friendly tail instructions, with automatic overflow and consecutive truncation recovery.
- **Post-compaction tool guards**: After compaction, stale whole-file `write` calls on existing unread files are blocked (while targeted `edit` patches remain allowed), and duplicate `read` ranges within the same epoch are deduplicated.
- **Lossless FTS5 episodic recall**: The WAL SQLite store maintains a contentless FTS5 `1..=3` Unicode n-gram index (with automatic in-memory fallback when persistence is disabled). Once the first prune/compaction happens or when running in a `/tree` fork lineage, `recall_search` and `recall_read` activate automatically so the model can search and read verbatim history across compaction boundaries.

## Pinpointing Slowdowns With `/trace` (<kbd>Ctrl</kbd>+<kbd>T</kbd>)

Ever felt a request drag on without knowing whether time-to-first-token was slow, the model's reasoning chain ran long, or a single tool call stalled for minutes? Press <kbd>Ctrl</kbd>+<kbd>T</kbd> (or run `/trace`) to launch the full-screen interactive trajectory analyzer.

The trajectory analyzer lays out every interaction along a shared millisecond timeline composed of three linked regions:

- **WaveBand**: Gives an instant bird's-eye view of turn-by-turn activity density across the session, helping you spot which turn triggered a heavy burst of tool calls.
- **Timeline**: Displays parallel swimlanes lining up LLM streaming responses, concurrent or sequential tool execution spans, and retry or timeout stalls on the same axis.
- **Hotspots**: Automatically ranks spans by wall-clock duration so the slowest calls appear right at the top, immediately revealing what drove total latency.

### Keybindings Inside the `/trace` View

- <kbd>Tab</kbd>: Cycle focus across panels and list panes
- <kbd>m</kbd>: Switch between statistics and timeline display modes
- <kbd>/</kbd>: Type a keyword to filter specific tool names or spans
- <kbd>Enter</kbd>: Expand full timing breakdown and detailed metadata for the selected span
- <kbd>Esc</kbd>: Close the trajectory analyzer and return to the conversation

<Callout type="tip">

Keep the distinction between `!` and `!!` in [Local Bash Mode](/en/tui/bash-mode/) in mind: strictly local `!!` commands do not trigger LLM requests and therefore never add to model time-to-first-token latency. When diagnosing model throughput bottlenecks, focus on the LLM invocation spans inside `/trace`.

</Callout>
